01 · System map

One composition, distinct client and server artifacts

Reuse compatible DOM workspaces and the current scope rules. The app contains fixed public client assets; the server retains business operations, data, grants and workers.

Source authority

Product + modules

Exact product definition, reviewed module manifests and module-owned UI.

Mobile target adds app identity and platform configuration. It does not choose another module set.

→
Construction

Reviewed mobile assembly

Resolve selected workspace exports, bundle assets and native adapters, validate compatibility and record hashes.

Fixed recipes; no executable URLs in runtime configuration.

→
Phone

Installed product app

Mobile shell, shared client scope/session core, selected domain workspaces and narrow native adapter.

Safe areas, keyboard, Back, resume, tenant selection and accessible navigation.

Network boundary: a fixed HTTPS endpoint and real user-authentication profile. The current loopback cookie profile cannot simply be exposed to phones.
User identity

System-browser sign-in

Authorization code with PKCE, protected credential custody, logout/revocation and original-session checks. No embedded service credential.

Application server

Existing module operations

Server-owned product, instance, tenant and actor. Current grants and module mode are checked on every operation.

Data ownership

Domain databases and jobs

Service Desk owns requests. Knowledge owns documents. The mobile shell does not create a universal record store or run server jobs.

Why this route: the current modules render into DOM elements. Capacitor offers a native container for web assets; React Native would need new module screen implementations. Confirm the choice with a short device feasibility gate. Capacitor runtime · React Native components

03 · Delivery sequence

A useful vertical slice, then repeatable production

The mobile UI and shared identity/network contract can be prepared independently. They meet before the first real device acceptance. Every milestone below is proposed and unstarted.

  1. M0

    Design and feasibility

    Confirm target platforms, approve screens and select auth/tooling. Launch a neutral fixed-asset probe on an Android device.

    NOT STARTED
  2. M1

    Shared client and mobile shell

    Extract scope/session behavior with web parity. Build mobile navigation and lifecycle with controlled transports.

    NOT STARTED
  3. M2

    Authenticated device reads

    Real phone sign-in and Service Desk reads over the selected HTTPS profile. Prove expiry, revocation and tenant isolation.

    NOT STARTED
  4. M3

    Complete Android pilot

    Create one real request and see it in the existing app. Verify repeated taps, network interruption, process death and resume.

    NOT STARTED
  5. M4

    Reusable factory and Studio target

    Source-derived mobile targets, fixed builds and separate artifact inventory. Generate a second composed product without changing the mobile host.

    NOT STARTED
  6. M5

    iOS and delivery qualification

    Repeat the real journey on an iPhone using a macOS/Xcode build host. Signing and distribution have their own recorded acceptance.

    NOT STARTED
Required before authenticated device acceptance: select a reachable HTTPS test endpoint, an identity provider/user-session profile and actual device/build hosts. These are explicit prerequisites, not features supplied by installing Capacitor.
