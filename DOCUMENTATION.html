FOUNDATION 0.2 · Start and run

Quadbridge Product Platform — Foundation 0.2

Complete corrected source, compiled local products, regression tests and developer tools. This release fixes review findings R01–R10 in the reusable platform. It is still a local developer preview, not a production-qualified platform or a Veyviz replacement.

The maintained Web shell, backend host, worker host and composition code are shared packages. Products supply definitions; domain modules own their business records. No camera, AI model, private repository or external database server is required by these reference products.

Run the included build

Requires Node.js 22.16 or newer. Execution was verified on 22.16.0, where node:sqlite is experimental. Other versions are not independently qualified by this delivery.

npm run setup
npm run demo

No package download is required for these two commands. setup creates local workspace links; the launcher starts the included compiled products and prints generated local admin / viewer credentials.

Try the connected example

Sign in to Knowledge, add a titled document and allow the worker to index it. In Cross-product handoffs, use that document ID and a request reason. Service Desk owns the resulting request; Knowledge shows destination acceptance, local job status and its own workflow separately.

The mapping org-a → customer-a is explicit. The destination service receives create and original-receipt-read permissions, not ordinary document or Service Desk list access. A known destination commit can coexist with a failed/cancelled local attempt. An authorized Check original receipt action can reconcile it; it is not a resend.

Service Desk's Request overview is a second named workspace, implemented through a lazy helper and declared CSS. It is a real multi-file assembly proof, not a second business backend.

Updating from 0.1

Use a new extracted directory. Do not recursively copy over an active checkout or automatically reuse old data/configuration.

Old pending v1 handoffs are held for explicit original-protocol reconciliation, not resent via v2. New grants are not silently added to existing seeded principals.

FOUNDATION 0.2 · Architecture

Product-neutral construction architecture — Foundation 0.2

1. Decision and source precedence

Build a reusable construction framework with maintained application hosts, optional capability implementations, domain-owned modules, explicit instance bindings and controlled cross-product integration. The platform itself is the first engineering deliverable. The two small domain applications are acceptance consumers—not a requirement to finish Veyviz before the platform.

The supplied Veyviz Platform Architecture Authority v1.6 describes a CCTV/AI product-family target, not this implemented neutral framework. Its small neutral foundation, public ownership boundaries, static reviewed contributions and separation of logical modules from deployed processes are retained as design inputs. The user's later platform-first direction governs this independent repository. This document does not revise Veyviz's authority, move its records, or replace its CapabilityPack catalogue.

reference/Veyviz_Authority_v1.6.md is preserved as source context only. Its Veyviz-specific job, source, topology, grant and release bindings are not copied into this platform's neutral contracts. In particular, earlier Forensics persistence language is not used to reclassify any current Veyviz records.

2. Governing structure

A package is not automatically a service. The backend and Web-serving adapter share one process in this profile. The worker is another process only for products that select background work. Domains use separate owner databases on the same local filesystem; separate schemas do not imply a database server per module.

3. Three independent graphs

Source dependencies: neutral packages do not import reference-domain packages. Domain code consumes public framework interfaces. Solution-owned adapters consume the participating public capabilities. Products supply configuration; no if customer or camera context enters the core.

Runtime collaboration: a source domain can call a destination public operation locally or remotely. Requests/results can flow in both directions without introducing import cycles or shared writable business data.

UI containment: navigation hosts a domain workspace. A DOM/React parent does not become the owner of the displayed record. Closing that workspace cancels view reads but does not cancel an accepted durable job.

4. Mandatory mechanism versus selected adapter

Module composition and public boundaries are neutral mechanisms. An authenticated-app profile selects identity/access and persistence implementations. The supplied local profile uses one working implementation instead of many empty adapter classes.

No product is forced to select jobs, knowledge, Service Desk, AI, video, sensors, notifications or reporting. A headless worker uses the corresponding host contract and does not require browser assets to start. The neutral application has no domain workspaces and no worker process.

The Node HTTP adapter delegates protocol handling to Node's standard HTTP server. SQLite is an explicit local adapter, not a universal domain repository. Browser DOM APIs render the first reference modules; React is an optional renderer integration seam. Hosted Nest/React/PostgreSQL/OIDC adapters are future supported-profile work, not silently implemented by naming them.

5. Contract and provider ownership

A business module owns the meaning of its exported operation. A consumer can request a narrower port. A solution adapter makes the mapping explicit. The framework validates registration and lifecycle but never invents an operation's domain semantics.

The reference public capability family is:

  • knowledge.document.read.v1: returns a permitted original document record from Knowledge.
  • desk.requests.create.v1: retained original owned create operation for existing consumers.
  • desk.requests.create.v2: opt-in cross-product operation returning a validated committed-resource receipt; original-receipt lookup is separately authorized.

Handoff selects the explicit v2 destination contract and depends on these meanings, not their repositories. Its adapter reconstructs a destination-owned context and enforces that provider's current module mode and grants. A source permission is not destination permission. A returned resource reference is not an access credential.

Contracts and module package versions are separate identities. The initial resolver deliberately supports exact versions and one module ABI; it does not claim arbitrary SemVer-range or binary compatibility.

6. Composition and instance scope

  1. Product selection identifies exact module versions and required bindings.
  2. Build creates .artifacts/<product>/plan.json, static frontend registration, selected backend registration and executable fingerprints.
  3. Application startup verifies its selected executable files and plan, loads reviewed local factories, applies compatible owner migrations, and starts modules in dependency order.
  4. Scope activation combines selected code with a real principal, tenant grants and module mode.
  5. Each request/workspace/job has its own lifetime and records.

A binding distinguishes contract, implementation, instance ID, consumer, lifetime and local/HTTP placement. The scoped-binding utility demonstrates application-, module- and request-cache isolation. The supplied reference solution deliberately accepts only application-scoped, stateless ports; it rejects unsupported shorter-lived adapter declarations rather than pretending they are wired. Request-scoped resource-bearing adapters must integrate actual disposal with the host that owns them.

Eager local bindings add provider-before-consumer construction dependencies. Binding-only cycles fail resolution; remote providers do not become hidden local modules.

Commercial plans are not implemented here. Product manifests select software; LocalAccess independently supplies developer-scope grants. Veyviz's actual commercial catalogue remains untouched.

7. Ownership, persistence and writes

Each module receives its own data path and creates a concrete owner repository. The foundation does not own a universal Person/Asset/Document/Incident table.

SqliteOwner.command() checks authority, starts an owner-local transaction, reconciles the original command key and digest, runs the domain change, and commits the result receipt/audit. The same identity and normalized input return the original result; changed input conflicts. Permission is checked again before returning an old receipt.

Knowledge inserts its document and indexing job in the same owner transaction. Handoff inserts its relationship and delivery intent in its own transaction. Service Desk independently commits the destination request. No transaction spans these databases or a remote server.

This profile is deliberately bounded: short synchronous SQLite transactions, limited row sets, one local filesystem, no horizontally distributed database protocol. A production adapter must preserve the same selected invariants, not merely offer generic CRUD.

8. Background execution and external uncertainty

A job has a stable identity, actor/tenant/permission binding, deadline, attempt, lease token and due time. A worker claims it atomically, rechecks current permission and module mode, prepares work outside the transaction, and commits only while its lease still owns completion.

The worker consumes the neutral JobExecutionStore port from packages/contracts, not a concrete database queue. Store calls may be asynchronous; finish() is awaited. The selected adapter owns the atomic completion relationship. An independent ephemeral conformance adapter exercises the same host with SQLite absent; this does not qualify another production store.

The completion callback and final job status share the owner transaction in the SQLite adapter. A stale attempt cannot update domain state. Computation may happen more than once; the code does not promise exactly-once execution.

A cross-product timeout means destination acceptance is unknown. Retry uses the same remote command key. The receiving owner deduplicates inside its business transaction. Handoff separately owns a durable delivery-fact row, its technical job, and its business relationship. A validated receipt is retained before local business completion is attempted. Revocation, cancellation, lease loss or exhaustion may prevent business completion but cannot turn known external acceptance into nonacceptance.

A narrow fact-only recorder can retain the outcome of an already dispatched operation without granting new dispatch or business-write authority. Explicit handoff.reconcile performs a destination receipt lookup (never a resend), then the source owner validates current authority before adopting its relationship outcome. A failed/not-found lookup leaves acceptance uncertainty intact. No generic model agent or automatic new-identity retry is used.

Queued cancellation is immediately cancelled. Running cancellation is a request; the active attempt must settle or expire before its cancelled outcome is recorded. Lease expiry fences commits; it does not prove physical compute or an external action has stopped. The supplied handlers do not run native GPU tasks.

9. Cross-product modes

Composed mode: Combined selects the Service Desk, Knowledge and Handoff modules in one application. Each still owns its persistence. A local adapter invokes the real Service Desk operation under the configured service principal.

Connected mode: Knowledge runs separately and calls Service Desk's fixed HTTPS-capable command adapter. The local proof uses loopback HTTP. Its org-a → customer-a mapping is explicit; tenant IDs are not assumed equal. The reference service credential has desk.create and desk.receipts.read, not document-read or ordinary Service Desk list authority. Original-receipt reads are limited to that actor and tenant. A receipt-only grant can be used without create authority.

The destination preflight resolves actual authenticated product/instance/tenant/service-actor identity. Mutation also checks the expected destination headers before executing a command. The returned quadbridge.command-receipt.v1 must match the explicit contract, original key, destination, actor and committed resource type/version. HTTP 202 or a bare ID never proves business commit. This is a declared opt-in receipt protocol, not a global semantic wrapper inferred from any successful HTTP response.

Only the fixed command and receipt paths and origin from trusted instance configuration are usable. Request data cannot choose a URL, credential or destination tenant. Redirects are refused. The source cannot impersonate its user at the target merely by forwarding an identifier.

10. Frontend and renderer contract

The shell owns authentication UX, product metadata, selected tenant, stable workspace paths, coarse failures and lifecycle. The domain workspace owns its content surface only.

A workspace receives root, immutable scope/permission views, AbortSignal, limited own-module API operations and a notification callback. It receives no session token, repository, framework-private store or mandatory site/floor/document fields. Dynamic imports come from build-generated static maps, never request data.

The same shell uses sidebar or top navigation according to the product definition. Domain views may use native DOM or a supplied React root adapter; the framework does not impose the reference form design on all products.

Requested tenant selection and accepted bootstrap are different states. Scope changes abort old work, clear old nodes and remove obsolete bootstrap immediately. Navigation cannot mount old metadata while a replacement is pending. Each workspace API captures the same immutable accepted scope as its displayed context, checks its generation before dispatch and after return, and cannot act on a different selected tenant. Background jobs remain owned by the server. Access refresh and workspace generation are fenced separately. Unchanged metadata preserves a valid current view, but successful recovery remounts one cleared by a failed refresh. The loader uses the exact declared own workspace export and validates its mount shape. Browser tests covering these behaviors are authored but environmental browser navigation was blocked in this session; no browser qualification is inferred from type checking.

Selected frontend build profile

The product build creates the complete selected native-ESM dependency closure: static imports/exports, literal dynamic imports, literal URL assets and module browserAssets. Nested helpers and assets are served through the generated allowlist and included in release hashes; web metadata is itself hashed. Backend entrypoints and unselected domain assets remain unserved.

Unknown/server-only packages, escaping paths, symlinks and nonliteral dynamic imports are rejected. CSS/assets are declared separately rather than imported as native JavaScript. This is a deliberately narrow build adapter, not a general bundler or a qualified React profile. A real third-party renderer/bundler integration remains separate work.

Local scheduling policy

Module queues use round-robin selection. The SQLite adapter rotates due tenant partitions and advances bounded per-tenant keyset scans, preserving cursors across restarts. Paused work cannot permanently pin the first candidate window. Technical stop reason is separate from the last execution error. A non-reentrant worker prevents overlapping ticks from claiming extra work.

Fair claiming does not preempt a long handler or guarantee a fixed wall-clock response time. The single local worker still requires short/cooperative preparation or a separate qualified compute adapter for heavy work.

11. Disablement, migration and upgrades

enabled permits authorized reads and writes. read-only retains permitted history but denies new commands and pauses new job claims. off denies the module's operations and removes its workspace. The code does not confuse those modes with package installation or data purge.

Migration history is hashed and ordered. Editing an applied migration or opening a newer unsupported generation is rejected. Reader/writer changes require owner-specific evolution. Removal assessment reports dependents, retained records and pending jobs; destructive uninstall, data purge, global rollback and historical-reader migration are not implemented.

Handoff migration 1 remains byte-identical; migration 2 preserves old protocol rows and adds delivery facts. Existing pending v1 commands are not automatically retried through v2, whose receipt namespace is different. They require original-protocol reconciliation. New permissions and bindings are explicit; existing seeded principals are not silently regranted.

Package versions and per-product build records support explicit adoption. Two actual 0.1/0.2 local neutral runtimes were exercised independently, with the older executable and reported version unchanged. This is narrower than published package adoption or shared-data rolling migration. This release does not claim a tested rolling upgrade between two independently published framework versions. Exported products contain fixed package versions; they are artifacts of the maintained source, not a recommendation to edit forked shell copies.

12. Verification and admission to broader use

Actual checks cover exact composition and provider ordering, owner transactions, migrations, role/tenant negatives, job restart and fencing, queue fairness, an independent worker process, local and HTTP cross-product commands, typed receipts and failure-state preservation, receipt-only reconciliation, multi-file asset closure, neutral export, a generated module without host edits, and a worker-store replacement with SQLite absent. Shell transitions run against actual compiled code using controlled document/event/request ports, not a real browser.

The next engineering work is to complete real browser/React acceptance, production identity/storage/runtime adapters, package publication/version adoption, resource limits for real workloads, operational lifecycle and a selected consumer adapter for existing Veyviz. Do not replace Veyviz's owners, grant model access, or declare production readiness from this developer-profile proof.

13. Remediation records

The R01–R10 implementation map, regression identities and limits are in docs/REMEDIATION.md. Source compatibility, legacy pending commands and new explicit permissions are described in docs/UPGRADE_FROM_0_1.md. These updates refine the same framework rather than introduce new business owners.

Cross-product state is three-dimensional

  1. Delivery fact: original destination/command, dispatch uncertainty, validated receipt.
  2. Technical job: queued/running/failed/cancelled/expired/succeeded with attempts and stop reason.
  3. Source workflow: the Handoff owner's adopted business state.

A destination receipt can be retained after local write authority or a worker lease is lost. Its fact-only recorder can update only that existing delivery's receipt; it cannot dispatch another request or mark business completion. The normal worker or explicit handoff.reconcile operation must still satisfy current owner authority before adopting the source outcome.

An UNKNOWN record remains UNKNOWN when retries expire. A read-only destination lookup uses the original actor/tenant/command key and requires desk.receipts.read. Lookup absence/error does not prove no prior commit. Receipt retrieval grants no ordinary destination record-list or document access.

Connection identity includes implementation/binding revision, actual product/instance, service actor, contract, tenant mapping and destination path/origin. Credential bytes are excluded from the binding identity: rotating a token for the same principal need not retarget an operation. Changing the principal or destination cannot silently replay an unresolved operation under a different receipt namespace.

Scheduling bounds and their limits

The host rotates among ready module stores. The SQLite adapter rotates tenant partitions and scans at most 16 due tenant partitions and 100 candidate jobs per selected partition per claim. Cursor progress is persisted. These are local implementation defaults, not throughput/SLA guarantees.

Claim fairness does not preempt a long handler. A synchronous blocking handler can still delay a single-process worker; native/CPU-heavy work requires the separate execution profile already described in the architecture. Lease fencing is not proof of external-action reversal or physical compute termination.

Frontend profile and replacement proof

The supported closure includes static imports/exports, literal import(), literal new URL(..., import.meta.url), and browserAssets copied from the module's source tree. CSS dependencies are included. Absolute/unselected/server-only imports and nonliteral dynamic imports fail build. This is a bounded native-ESM profile, not a general-purpose replacement for Vite/Webpack or a complete React build adapter.

The second worker-store implementation is ephemeral test/conformance code. It proves the host's dependency boundary, rollback behavior and async compatibility without SQLite. It does not establish production persistence, distributed queue semantics or durability after process loss.

Compatibility

Framework packages and product definitions select 0.2.0. Module ABI naming remains v1, but 0.1 framework package mixing is not promised. Public Service Desk v1 stays available; v2 is explicit for new integrations. Handoff schema migration 1 is unchanged; migration 2 preserves old data and blocks legacy v1 automatic resubmission. Read UPGRADE_FROM_0_1.md.

FOUNDATION 0.2 · Upgrade safely

Adopting Foundation 0.2 from 0.1

Recommended path

Extract the complete 0.2 archive into a new directory. Run npm run setup, then npm run demo with new local data. Keep the original source and data intact. This is a local framework preview, not an automatically managed production upgrade.

The accompanying source patch is for the exact original 0.1 archive, not an arbitrary checkout. Use git apply --check first and review changes. The patch does not contain refreshed compiled output: run the build using the pinned development tools before starting patched source. The complete archive already contains the updated compiled products.

Package and browser compatibility

All maintained packages, reference modules and selected product definitions are 0.2.0. Rebuild an exact composition; do not mix 0.1 clients with 0.2 framework packages merely because the module ABI retains its v1 name. There is no independent published-package rolling-upgrade guarantee.

The browser loader now honors the exact export name. Modules can use selected multi-file native ESM and declared assets. Unsupported bare browser imports fail build rather than being exposed through the server. Existing single-workspace examples remain valid.

Explicit destination contract

Existing human GET/POST /api/requests and desk.requests.create.v1 remain. New cross-product wiring selects:

  • desk.requests.create.v2 and POST /api/requests/commit for an explicit COMMITTED receipt;
  • GET /api/requests/receipt?commandId=... for lookup only;
  • exact destination product, instance, tenant mapping and destination service actor;
  • original command identity preserved across retries and receipt reads.

desk.receipts.read permits only the authenticated actor's original v2 receipts in its permitted tenant. It does not grant normal desk.read. handoff.reconcile permits the source's explicit reconciliation operation. The fresh local example seeds these grants; existing seeded principals are not silently changed. An operator must review and deliberately apply any local grant/configuration migration, or use a separate clean preview data directory. Do not hand-copy secrets into source.

Existing local data

Service Desk's existing migration is unchanged. Handoff migration 1 is unchanged. Handoff migration 2 adds a protocol marker and an owner-local delivery-fact table. Queue metadata adds a separate stop reason and scheduling cursors. Tests exercise old schema preservation and refusal of edited migration history.

These migrations do not supply a backup/restore system. Preserve a consistent stopped local data copy before experimenting with existing data. Opening migrated Handoff data with old 0.1 code is not supported and must not be called rollback.

Legacy pending cross-product operations

A v1 destination command may already have committed even when the old source records no receipt. Do not send that old operation through v2: the receiver's operation/receipt namespace changed, so it could create a second resource.

The 0.2 source retains those v1 rows and reports RECONCILIATION_REQUIRED; already accepted v1 rows retain their target references and are labelled legacy. It does not fabricate a v2 receipt, silently rewrite the old command identity or automatically resend.

Resolve a legacy pending operation through its original receiver/actor/tenant/command protocol and an explicit reviewed migration. An automated legacy reconciliation tool is not included. This deliberate hold is safer than duplicating a cross-product business action.

New v2 operations

A recorded COMMITTED receipt can coexist with a failed/cancelled local job. UNKNOWN remains after timeout, cancellation or exhaustion. The authorized Check original receipt action checks the original command without resending. Source business completion still passes its owner command and current authority. Technical attempt history is not rewritten to look successful.

Changing a destination binding or service principal for a pending operation requires reconciliation rather than retargeting it. Same-principal credential rotation is distinct from choosing another identity.

What the version exercise proves

tools/version-isolation.mjs --older-root <original-0.1-directory> runs actual old/new neutral snapshots in separate temporary local instances and verifies the older runtime stays on 0.1 with unchanged executable bytes when 0.2 starts.

It does not prove published package distribution, shared-data migration rollback, browser compatibility, production rolling upgrades or fleet operation. See evidence/version_isolation.json.

FOUNDATION 0.2 · Developer guide

Building a product with this framework

A normal new product

Run the factory's create-module and create-product commands in the root README. Generated files belong to the product/module. The shell and hosts remain shared package dependencies. npm run build generates static registrations from reviewed local manifests; no runtime file discovery occurs from customer input.

The module generator implements a real scoped item table, migration, GET, idempotent POST and UI. It does not decide your domain: replace the sample business behavior, add invariants/retention, and write acceptance tests before shipping it.

A module's actual entry point

export function register(env: ModuleEnvironment): HostedModule {
  // Construct only this owner's repository and supported ports.
  return { manifest: env.manifest, services, routes, close };
}

Routes must match the manifest's method/path/permission/kind. Unknown routes, duplicate contributions, host-auth route collisions and missing declared implementations fail startup/build. A typed manifest requirement is not an IAM grant.

Do not start tenant business work in register(). Registration sets up repositories and handlers. A public operation or admitted worker starts scope-specific work.

Backend operations

Use module-specific input parsing. The helper object() rejects unknown fields, but it is not a replacement for domain validation. Keep conditional updates and invariants under the owner. Use the receipt/transaction helper only where its semantics fit. Do not return an ORM entity merely because the example uses a small matching DTO.

Do not await inside SqliteOwner.transaction() or its command callback. Obtain external results before the transaction, then check current applicability while committing. Another module's database handle is never a public integration API.

Public capability and solution adapter

Declare the provided/required contract in module.json. A product binds the consumer to an exact implementation/instance. Local eager bindings add startup dependencies automatically and must be acyclic; HTTP bindings retain a remote provider. Its selected solution contributes the actual typed translation, currently illustrated by solutions/knowledge-to-desk/wiring.mjs.

A new capability needs a real adapter. The resolver does not pretend that matching strings generate its behavior. Put a new adapter in product/solution-owned code, not a giant switch in packages/backend-host.

Scope and identity

RequestContext is created after authentication and supplies tenant, product/instance and actor. assertAllowed is rechecked at consequential operations. A tenant header is only a selector. Reference rows have compound tenant/record identity.

For cross-product calls, use an explicit product/instance/tenant map and a destination-authorized service identity. The configured identity is validated against the actual destination and checked again at mutation. New reference Handoffs use desk.requests.create.v2 with an explicit committed receipt. Do not accept an HTTP 202 job ID as a committed record. Original receipt retrieval is a separate operation and permission. Source-user identity is not a forwarded grant. Dedicated service permissions and immutable request IDs make retries explicit. Do not hard-code production endpoints or credentials in a module.

UI contribution

export const workspace: Workspace = {
  mount(ctx) {
    // Build content inside ctx.root using your renderer.
    // Reads and subscriptions use ctx.signal.
    return () => { /* dispose this view's resources */ };
  }
};

Each declared workspace names its actual export, for example workspace or overviewWorkspace. The shell loads that exact export from the statically selected module and validates mount. Several workspaces can coexist in one module; they need distinct paths/IDs and correct permissions.

The supported native-ESM profile follows relative static imports and literal import('./ui/detail.js'). Declare non-code browser assets in module.json, for example "browserAssets": ["ui/detail.css", "ui/icon.svg"]; files are copied from the module's src/ tree. Literal new URL('./icon.svg', import.meta.url) is supported for tracked assets. CSS dependency files must exist in the declared/copied tree. Do not use Node libraries, arbitrary dynamic import strings or undeclared browser packages. A different third-party bundler/React build profile is not implemented by this scanner.

The module is statically known; code loads only when the selected workspace is mounted. Generic host API calls are restricted to that contribution's declared own-module operations. Additional public capabilities must receive a deliberate host adapter, not an unrestricted fetch object.

A workspace context and its API are bound to one accepted scope. After abort, do not submit new calls; late results and notices cannot update another generation. Requested tenant selection is not an accepted scope.

Do not mutate another workspace's state. Do not equate unmount with cancelling a durable server job. Add separate backend cancellation only when its operation semantics require it.

Worker handler

Worker registrations use JobExecutionStore from the neutral contracts package. The host does not import SQLite. Implement claim, renew, assertCurrent, finish and fail, retaining the adapter-owned atomic completion relationship. These calls may be async; the local reference adapter stays synchronous. The independent memory adapter under tests/fixtures is ephemeral conformance code, not a replacement production database.

Prepare expensive work outside the transaction. Return a short commit() callback that applies its owner-local result. The worker verifies its current lease and authority before that callback. Use stable identities for external effects that may occur before commit; never claim a database transaction can undo a remote operation. The handler receives a current job/attempt check; invoke it immediately before an external dispatch and durably mark uncertainty. Record received external facts separately before a source business completion that may be refused. Read-only reconciliation must not submit another effect.

The reference scheduler rotates modules and tenant partitions with bounded advancing eligibility scans. This prevents the reviewed starvation but does not preempt a long-running handler or guarantee latency under arbitrary load.

The reference index is bounded text processing. Long native tasks require a supported execution adapter with physical resource admission and confirmed cleanup; the generic worker's lease alone is insufficient.

Reference HTTP operations

All requests use the local identity profile. Domain requests require X-QB-Tenant; writes require Idempotency-Key, JSON content and same-origin cookies or an approved service bearer identity.

Release adoption

Edit maintained source, rebuild, review the product plan and test applicable consumers. An exported directory is an immutable candidate artifact. Do not edit its shared package source and call that a framework upgrade. Published-package distribution, multiple supported release families and production rollout remain separate work.

Legacy integration warning

Do not retarget an old pending v1 handoff to v2. See UPGRADE_FROM_0_1.md. A protocol-compatible field shape is not proof of identical deduplication or completion meaning. Existing grants remain unchanged until explicitly migrated.
